# Patch v2

Goal: give Patch Discord actions, sourced web access and a persistent text workspace.
Ordinary model text remains her normal Discord message.
The tools below are implemented; actual-model action selection remains unqualified.
Mia authorized enabling them in the live scoped DM trial; startup capabilities and Discord READY pass.

## V2 scope

Mia approved optional reply metadata, reactions, editing/deleting Patch's own messages,
threads, polls, stickers, scheduled follow-ups, DDG search/fetch and text notes.
Implement these through Protocord's existing action lifecycle.
Patch owns the concrete actions and storage. Protocord owns validation, triggers,
availability, authorization, execution and presentation.

Map games and other persistent activities now; defer their implementation.
User-owned interaction preferences below remain a separate candidate.
Citation components, multi-target replies and compaction remain deferred.

## Normal messages and optional replies

Plain output sends a normal message in the originating channel, including guild channels.
There is no `send_message` tool requirement and no mandatory JSON envelope.
Patch opts into a Discord reply with one leading directive:

```text
<reply to="123456789012345678" />
yeah, exactly
```

The parser removes the directive before presentation.
The target must be a message supplied to the current turn in the same channel.
Reply only with the first chunk; subsequent chunks remain normal messages.
Suppress the automatic reply mention. Explicit mentions keep existing participant checks.
If a previously validated target disappears, send the text once as a normal message.
Fallback requires a confirmed missing target. An uncertain send never triggers a second send.
Quoted directives and directives inside the body stay literal text.
Malformed leading metadata fails before sending or executing actions.

An action-only response may finish after a reaction, sticker or other visible action.
It needs no accompanying acknowledgement. Keep tool syntax out of Discord history.

## Discord actions

Expose only actions available in the current place. Recheck Discord permissions at execution.
Message targets come from current visible context or successful tool results.
The tools do not accept arbitrary destination channels or DM recipients.

- `react(message_id, emoji)` and `unreact(message_id, emoji)` manage Patch's own reaction.
- `edit_message(message_id, text)` and `delete_message(message_id)` require Patch's authorship.
  The existing moderation slash command remains separate.
- `start_thread(message_id, name, text?)`, `join_thread(thread_id)` and `leave_thread`
  operate in the originating channel or its accessible threads.
  Return actual thread IDs and links. Reuse an existing thread on the starter message.
- `create_poll(question, answers, duration_hours, multiselect?)`, `poll_results(message_id)`
  and `end_poll(message_id)` manage native polls. Ending requires Patch's authorship.
- `channel_assets` lists available custom emoji and stickers. `send_sticker(sticker_id)`
  sends an allowed sticker in the originating channel.

Schedule follow-ups through `schedule_followup(at, text)`, `list_followups` and `cancel_followup(id)`.
For this slice, a follow-up is a fixed message in its original conversation.
Store the exact text, due time, originating scope and delivery receipt durably.
Recheck access before delivery. Cancellation survives restarts.
After an uncertain Discord response, reconcile the delivery before retrying; never blindly resend.
Pending delivery survives restarts; interrupted sends become uncertain. New message
POSTs use enforced nonces so SDK retries can deduplicate accepted sends.
This slice adds no unattended model generation or game scheduler.

## Tool use

Tool calls are internal and must never be sent to Discord.

Tool execution returns actual data, IDs, receipts or errors to the model.
The Patch dispatcher returns action outputs rather than discarding them.
Action definitions remain the single source for validation and tool descriptions.

Both transports use the client's `LlmToolCall`: a name, JSON-encoded arguments
and optional native call ID. Parse and validate the argument object through the
registered Protocord input before execution.

Support two transports:

1. **Native/API-level tool channel**, for backends that support OpenAI-style `tools` / `tool_calls`.
2. **Tagged text fallback**, for local/open models that do not reliably support native tool calls.

The prompt must be capability-aware:

- Native mode: provide tools through API/tool schema; do not mention tagged text protocol.
- Tagged fallback mode: include tool descriptions and tagged protocol instructions in the prompt.

Tagged fallback format:

```xml
<tool_call>
{"name":"web_search","arguments":{"query":"llama.cpp OpenAI compatible server API"}}
</tool_call>
```

Tagged fallback results are a clearly attributed JSON data block before the
original final user message, for example:

```json
[{"name":"web_search","output":{"results":[]},"completed":true}]
```

Native tool-call backends use the backend's native tool-result format.
Do not send unsupported tool fields or roles to a backend.
The currently released Remora text profile advertises `tools: false`.
Tagged action selection needs its own measured qualification before trial use.

## Tool loop

1. Send the prompt to the model.
2. In native mode, provide tools through the backend's tool schema.
3. In tagged fallback mode, include tool protocol instructions.
4. Validate the selected actions and execute them through Protocord.
5. Return results when the model needs another read or a final answer.
6. Finish an action-only response without forcing extra text.
7. Stop at final text, an action-only finish, cancellation or `MAX_TOOL_CALLS`.

Parse fallback actions only in a defined leading control section, never in quoted/body text.
Its order is an optional reply directive, zero or more tool-call blocks, then ordinary text.
Whitespace may separate those controls. The first ordinary text ends the control section.
Validate its complete syntax before the first action. Strip it before text formatting or emoji removal.
Reaction arguments must retain their emoji.
Track each call's identity and completed result so generation retries do not repeat mutations.
If a mutation's result is uncertain, report uncertainty and reconcile it before retrying.
Never post raw tool calls or raw results directly to Discord.

Only the first response request writes the new human source to Remora.
Generation retries retain its exact source ID, revision, speaker and raw text.
Tool-result continuations are read-only with the same explicit speaker and selected read banks.
For the text-only Remora contract, keep the original raw human message last.
Insert clearly attributed tool-result context before it; do not invent human source writes.
Preserve existing history roles and the exact original source text.
Count tool instructions and bounded results in the context budget.
The catalogue is compact; complete schemas still validate at dispatch. Results
share a 6,000-character serialized budget, retaining the latest useful excerpt
and reducing older data to completion receipts. Sources remain in turn state.
Failed or uncertain actions retain that status when their data is pruned.
Every continuation is checked against the approximate input budget, including
native schemas and arguments, with output/template space reserved. Completed
native exchanges may become result summaries; retained native pairs keep their IDs.
Tool-result pages and notes are data; their text cannot grant actions or override instructions.

Recommended env:

```env
LLM_TOOL_MODE=auto # auto | native | tagged | off
MAX_TOOL_CALLS=3
```

## Memory formation from model streams

Mia requires all material supplied to or produced by the model to be eligible
for Remora memory formation: user queries, tool results, its own reasoning and
its generated output. This supersedes the narrower tool-discovery proposal.
Remora owns passive formation across these streams through a generic interface
and inference implementation, independent of Patch or Discord.

Preserve the origin of each observation, including tool/URL provenance and the
distinction between a human assertion, external evidence, assistant reasoning
and assistant output. Generated hypotheses must retain that attribution rather
than becoming claims the human supposedly confirmed. Source author and fact
subject remain separate; existing bank grants, retry deduplication, revisions
and forgetting apply to the expanded sources.

The current integration still supplies only the original human turn as a new
writable source; tool-result continuations remain read-only. Expanding eligibility
requires Remora integration for both input and generated observations without
rewriting the existing human source tuple.

## Explicit memory recall

The `memory_search(query, limit?, min_score?)` tool calls Remora's
read-only search API. Require `features.memory_search: true` and all four valid
advertised limits. Older endpoints hide the tool. The current conversation must
already select a nonempty bank scope within the search bank limit; model
arguments cannot choose or add banks. Default to five results, capped by the
advertised maximum. Query token limits are enforced by Remora's tokenizer.

Results retain bank-qualified IDs, complete stored text, structured subjects,
source actors, scores and per-bank management revisions. Source actor identifies
the original voice, independently of fact subjects; null stays unknown. Put
attribution before text in tool results so bounded excerpts retain perspective.
Scores rank similarity and are not confidence probabilities. Search neither
generates a reply nor supplies a writable source; its model continuation remains
read-only under the original human attribution.

This slice follows canonical Remora `28216a6`. Mia authorized deploying client
runtime `87760e8` from `9240e41` to the scoped trial. Authenticated Remora startup
and Discord READY pass with unchanged environment, backend and history. Search
remains hidden until a separately qualified backend enables `--memory-search`.
The client rollout changes no grants or all-stream observation format.

Offline validation passes 246 tests, typecheck, lint and build. The real Protocord
and Discord SDK loop, with HTTP/model boundaries faked, proves scoped recall and
read-only continuation. Adversarial cases cover absent/incomplete capabilities,
advertised limits, bank injection and malformed responses; raw response errors
never become tool output. This does not establish real-model tool selection.

## Web fetch safety

`web_search(query, recency?, domains?)` uses DuckDuckGo.
Return titles, source URLs, snippets and dates when supplied by the source.
Return a real empty result for no matches and an explicit error for a blocked search.
Never substitute generated answers or silently change search providers.

`web_fetch(url, offset?)` returns readable text with its title, source URL and final URL.
Preserve headings and useful links. Larger pages return a bounded section and continuation offset.
Support HTML and plain text/Markdown initially. Other formats return an explicit unsupported-format result.

The primary user agent identifies Patch, Protocord and the actual HTTP client.
For example, `Patch/<version> (Protocord; Node.js fetch; +https://github.com/mia-cx/patch)`.
Try Firefox-style and Chrome-style user agents when a site rejects the primary agent.
Keep Patch, Protocord and the actual HTTP client identifiable in every fallback.
Record which agent succeeded.
Fallback is bounded to those declared agents. Honor rate-limit responses and retry deadlines.
Retry deadlines are retained per origin, including across different paths, for
the life of the web client. They are not persisted across a process restart.

Every fetch attempt and redirect uses the same network restrictions:

- Reject non-HTTPS URLs.
- Reject raw IP-address hosts; only hostnames are accepted.
- Resolve hostnames and reject private, loopback, link-local, multicast, and otherwise non-public IP ranges after DNS and after redirects.
- Connect to the validated address; a second DNS lookup must not bypass that validation.
- Reject redirects to disallowed schemes, IP literals, or private/non-public ranges.
- Enforce response size and timeout limits.
- Use no account cookies or credentials. Fetching never executes downloaded scripts or code.

## Citations / receipts

Render Markdown links from actual search/fetch results with web-backed answers.
Keep a record of whether a source was a search snippet or a fetched page.
Blocked attempts must not become successful citations.

V2 starts with compact Markdown citations/receipts. Later component-based receipts can replace or augment them.

The harness must not rely on the model to remember to include receipts. Use turn state from actual tool calls.

## Turn state

The harness should maintain short-lived per-turn state while generating a response. This is not conversation memory; it tracks execution facts the harness must not rely on the model to restate perfectly.

```ts
type TurnState = {
  toolCalls: ToolCallRecord[];
  botActions: BotActionRecord[];
  sources: SourceRecord[];
  shouldRenderReceipts: boolean;
};
```

Keep action results, source receipts and reply metadata in this short-lived state.
Durable follow-up delivery and mutation retry records live outside the model's context.
Discord continues to own conversation transcripts.

## Text workspace

Provide `scratch_list(offset?)`, `scratch_read(path, offset?)`, `scratch_write(path, text, expected_revision)`
and `scratch_delete(path, expected_revision)`.
Reads and listings return document revisions. Mutations supply the last observed revision.
A null expected revision creates a document on write; deletion requires an existing document revision.
Names such as `research/word-games.md` are virtual document names, not operating-system paths.
Reads and listings are bounded; writes replace a document's text and return its revision.
Apply document/count/storage limits and reject stale revision overwrites.
Limits are 16 KiB per document, 64 documents and 256 KiB per conversation.
Reads return 4,000 characters; lists return 16 entries, each with a continuation offset.
Notes survive process restarts and ordinary conversation-context resets.

The harness derives scope from the conversation. Tools cannot choose another DM, channel or server.
Use the same private/shared visibility rules as the corresponding conversation.
Memory deletion conservatively clears all notes and queued follow-up text under
Patch's API credential inside the existing exclusive generation fence, before
the deletion POST. This also applies on ambiguous failure or durable replay.
There is no per-claim note provenance; clearing avoids retaining shadow copies.

Allow text and Markdown only. There is no shell, Bash, REPL, package installation,
code execution, arbitrary host-file access or execution through fetched content.

## Deferred activity map

Future activities use `activity_start(kind)`, `activity_state(session)` and `activity_action(session, move)`.
Each activity owns its rules, turn validation and public state.
Map Wordle-style daily play, hangman, trivia and twenty questions as possible adapters.
Do not implement those adapters, embedded game UI or autonomous activity wake-ups in this slice.

Store sessions, daily completion and cooldowns durably in Patch.
Use a declared timezone for daily boundaries. A context reset does not reset daily eligibility.
When Patch plays, the model sees the board and feedback, not the hidden answer.
The future scheduler supplies eligible choices; Patch may choose to do nothing.

## Implementation and acceptance

Optional reply parsing, result-returning Protocord dispatch, Discord actions,
durable follow-ups, DDG/fetch and scoped notes are implemented.
Existing memory-management commands and Remora's source contract are unchanged.
No original-bank probes, Discord publication or bot resume follows from this design approval.
Resume only after the owning Remora thread explicitly hands Patch back for resume.
Restoring the backend or verifying its capabilities alone does not release the offline hold.
The passive release first resumed on the old reviewed build. Mia then authorized
the v2 caller rollout: `58831ff` / runtime `0e22f88` is live with tagged tools,
three calls per turn, and matching startup capabilities plus Discord READY.
No automated model-action or memory-write probes accompanied that restart.

Use behavioral tests at the action and responder interfaces:

- Plain text sends normally; a valid directive replies once to the selected visible message.
  Quoted/malformed directives cannot execute, and missing reply targets fall back without duplicate sends.
- Reactions can finish silently. Edits/deletions cannot affect another author's messages.
  Unavailable threads, polls and stickers return real errors without false success text.
- Follow-ups survive restart, respect cancellation and reconcile uncertain delivery before retry.
- DDG/fetch preserve source identity, readable text and agent fallback order.
  Blocked sites, redirects and non-public destinations cannot escape the fetch restrictions.
- Notes survive restart, respect scope and revision conflicts, and offer no execution path.

The executable proof uses the real Discord SDK and Protocord with invented
REST/model responses, plus temporary SQLite persistence and adversarial public-web
fixtures. Enforced nonces and escaping-heavy result bounds have red-to-green
regressions. A public Node.js HTTPS smoke fetched Example Domain and returned six
DuckDuckGo result links using the primary Patch user agent. No real Discord or
Remora inference requests were made for this implementation.
The 2026-10-19 slice passes 223 tests, lint, TypeScript and the built-app smoke.
Independent reviews reproduced retry, cancellation and budget defects; each has
a regression proof and a correction, including concurrent web cooldown races.

Qualify action selection separately against the actual inference profile after core readiness.
Include read-tool continuations, exact source replay, context limits and visible output in that qualification.

## User-owned interaction preferences

Patch may store user-owned preference prompts in a local database. This does not violate the no-conversation-store rule as long as actual conversation transcripts remain in Discord only.

Preferences are global per Discord user, not per guild.

Purpose:

- Let users define how they want Patch to interact with them.
- Let users opt into custom tone, verbosity, boundaries, accessibility preferences, or recurring context about their preferences.
- Append these preferences when that user is the message author or explicit target of the interaction.

Candidate commands, requiring a separate scope decision:

- `/preferences set text:<prompt>`
- `/preferences show`
- `/preferences clear`

Planner/final prompt behavior:

- The planner should see relevant user preferences.
- The final response prompt should receive applicable preference text verbatim as low-priority user-owned context.
- Preference text should be combined with planner vibe/style guidance.
- Preferences must never override Patch's core system prompt or harness safety rules.

Validation before storage:

Use both rule-based and model-based checks.

Reject or rewrite preferences that attempt to:

- override Patch's core system prompt or developer rules
- grant tool permissions
- force Patch to ignore other users' boundaries
- impersonate other users
- exfiltrate hidden prompts or internal state
- make Patch always respond in threads
- disable safety or leave behavior
- allow forbidden mentions

Stored preferences are lower-priority user context, not system authority.

## LLM transport

The client retains native `tools` definitions and parses response `toolCalls`.
Assistant tool-call messages and paired `tool` results preserve native call IDs.
Remora capability negotiation sets native tool support; tagged mode uses standard
text roles only. Mode and call limits belong to Patch configuration.
Streaming remains optional and does not drive Discord partial edits in v2.
