# Patch v1

Goal: harden the Discord-native MVP after v0 proves direct Discord + LLM responses. v1 is still Discord + LLM only. No tools, no web search, no user preferences, no components, no compaction.

V1 promotes the main items deliberately deferred from v0: thread/forum participation, classifier/planner, robust queueing, and basic Discord commands.

## V1 scope

Implement:

- Thread/forum participation using Discord thread membership as canonical state.
- Classifier/planner on all triggers.
- Passive thread response TTL/drop behavior.
- Channel/thread-aware queueing.
- Classic reply-chain preceding-neighbor context.
- Split-response reconstruction, including multi-message `<response message_ids="...">`.
- `/leave`, `/model`, `/summarize`, owner-only debug commands.
- Context menu command: `Summarize this reply chain`.
- Rolling context window.
- Production-safe logging.

Do not implement:

- Tool calling.
- Web search/fetch.
- User preferences.
- Components/modals.
- `/compact` behavior.
- Streaming partial edits.
- Multi-target responses.
- In-flight cancellation/rewrite beyond timeout and stale queue drops.

## Discord permissions/intents

Use the basic permissions needed for text interaction and message context reconstruction. Adjust later when utility features are added.

Expected v1 needs:

- read messages / view channels
- message content intent, if required for the bot/application setup
- send messages
- send messages in threads
- read message history
- use slash commands / application commands
- create message context menu commands
- add/use external emojis and stickers where Discord requires explicit permission
- manage own thread membership / leave threads

Avoid broad moderation/admin permissions. Patch does not need role management, channel management, member management, or thread title editing.

## Thread membership

Discord thread membership is canonical.

- Patch becomes a thread member only when mentioned, relying on Discord's native auto-add behavior.
- Verified behavior: Discord adds mentioned bots as thread members.
- The harness should not expose or call a proactive thread-join operation in normal behavior.
- If Patch is a member of a thread/forum post, new messages are eligible for classifier/planner processing.
- If Patch is not a member, she ignores the thread unless mentioned.
- `/leave` or `@Patch leave` sends a farewell and then leaves the thread using Discord's thread-member API.
- Patch may silently leave if the classifier decides the conversation has become private, sensitive, or clearly no longer welcoming to bot participation.
- After leaving, Patch ignores the thread until mentioned again.

## Classifier/planner

Patch uses the classifier/planner on all triggers to choose response style, tone, and behavior.

For passive thread messages, it decides whether Patch should respond and how.

For manual triggers, it shapes tone/style but must not choose `ignore`.

Manual triggers:

- direct mention
- reply to Patch
- slash command
- message context menu command

Passive triggers:

- new message in a thread/forum post where Patch is already a thread member

Recommended output:

```json
{
  "action": "respond",
  "confidence": 0.82,
  "tone": "dry, casual",
  "style": "short answer with one quoted reference",
  "split_preference": "single_message",
  "reason": "The latest message asks an unaddressed question and Patch is the natural responder."
}
```

Allowed actions:

- `respond`
- `ignore`, only for passive thread messages
- `leave`
- `silent_leave`

If the planner chooses `ignore`, `leave`, or `silent_leave` for a passive thread message, the final response model is not called.

If the final response model is called, `action="respond"` is implicit. The response prompt should receive only compact style/tone/vibe guidance, for example:

```xml
<response_plan tone="dry, casual" style="short answer with one quoted reference" split_preference="single_message">
The latest message asks an unaddressed question and Patch is the natural responder.
</response_plan>
```

## Planner behavior

- Respond if the latest message is directly addressed to Patch.
- Respond if the latest message asks a question that does not appear directed at anyone other than Patch.
- Respond if the latest message appears to expect follow-up from no one other than Patch.
- Respond if Patch has valuable context and speaking would not feel unasked for or overstepping.
- Choose a response style appropriate to context: helpful answer, quick aside, correction, joke, emotional support, clarifying question, or quiet exit.
- Ignore side conversations between humans.
- Ignore ambiguous chatter when Patch is not clearly expected to participate.
- Leave if Patch is explicitly asked to leave, dismissed, or clearly no longer welcome.
- Silently leave if the conversation has shifted into something private, intimate, sensitive, or clearly human-to-human where a farewell would itself be intrusive.
- Prefer not responding when uncertain on passive thread messages.

`@Patch leave` can be caught before classification with a simple intent check and should usually produce `leave`, not `silent_leave`, unless context makes silence clearly better.

## Classic reply-chain context

For non-thread reply-chain interactions, include:

1. The upward reply chain from the triggering message.
2. Up to **5 preceding channel messages** immediately before the triggering message, marked `context="neighbor"`.

Do not include neighbors around every reply-chain ancestor.

Outside threads, newer neighbors after the trigger are not expected in the normal path. Race conditions are ignored for v1; work from the `discord.js` cache/fetch state available when the trigger is handled.

Reconstruction algorithm:

1. Start with the triggering message and already-cached/recent messages.
2. Build a map of known messages by ID.
3. Collect up to 5 preceding neighbors before the trigger.
4. Walk upward through `reply_to` references using cache/map when possible.
5. Fetch missing parents as needed.
6. Stop on no parent, fetch failure, max depth, or context budget.
7. Merge chain and neighbors, dedupe by message ID, sort chronologically.
8. Mark non-chain neighbors as `context="neighbor"`.

## Thread context

For passive thread messages and manual thread triggers:

- Fetch recent thread messages newest backward.
- Recommended limit: 30-50 messages or context budget, whichever hits first.
- Mark thread messages `context="thread"`.
- Include `reply_to` as a lightweight hint.
- Do not traverse downward into reply branches.

## Split-response reconstruction

Patch may send one semantic response as multiple Discord messages. In transcripts, normalize chained Patch self-replies into one `<response>` block.

Example:

```xml
<response message_ids="124,125,126" author_id="patch" author_name="Patch" timestamp="..." reply_to="123" context="reply_chain">
first chunk

second chunk

third chunk
</response>
```

When a user replies to the middle of a split Patch response, reconstruct the whole response.

Recommended v1 forward-fetch heuristic:

1. Walk backward through Patch self-replies to find the first chunk.
2. Fetch recent messages after the replied-to Patch message in the same channel/thread.
3. Include directly chained Patch self-replies that continue the same assistant response.
4. Stop when there are no newer messages to inspect, or after more than 3 non-Patch reply-chain continuation messages appear.

The “more than 3” tolerance handles people speaking before Patch sent the final split response chunk.

## Response behavior

- Send Discord typing indicators while planning/generating.
- Post only complete chunks. Do not stream partial edits.
- First chunk replies to the trigger.
- Later chunks reply to previous Patch chunk.
- Split at model-provided `<|message_split|>` markers (legacy `<split />` still accepted) outside code, including around headings, lists and quotes.
- Hard-split only when a chunk exceeds Discord's message length limit.
- The harness must not add conversational burst splits on its own.

Failure message after a manual trigger:

> sorry, brain fog. couldn't get my thoughts into a usable shape. try that again?

Passive thread responses may fail silently unless debugging is enabled.

## Queueing

Use a global generation queue with max global concurrency.

Recommended defaults:

- `MAX_GLOBAL_CONCURRENCY=1`
- passive thread TTL: 30 seconds

Priority tiers:

1. `/leave`
2. manual triggers: mentions, replies, slash commands, context commands
3. passive thread responses

Within tiers, use a smart combination of FIFO and round-robin:

- Bucket jobs by channel/thread.
- Preserve FIFO order inside each bucket.
- Round-robin across buckets so one busy channel does not starve others.
- Drop passive jobs that exceed TTL before generation starts.

No v1 in-flight cancellation/rewrite beyond timeout and queue stale-checks.

## Commands

V1 slash commands:

- `/summarize message:<url-or-id optional>` — summarizes a referenced reply chain or current thread. Outside a thread, requires a message URL/ID unless invoked through a message context menu.
- `/leave` — leaves the current thread/forum post.
- `/model` — shows configured model/backend information.
- `/debug-context message:<url-or-id optional>` — bot-owner only and ephemeral; shows reconstructed transcript and token estimate.
- `/debug-classify` — bot-owner only and ephemeral; shows how Patch would classify/plan for the latest thread message.

`/ask` is intentionally excluded because mentioning Patch covers ad-hoc prompting.

V1 message context menu commands:

- `Summarize this reply chain`

Context menu chain commands traverse upward through reply references only. They must not traverse downward into replies.

## Logging

- Production logs only failures/error traces by default.
- Prompt/transcript logging requires `DEBUG_LOGGING=true`.
- Debug logging must not be enabled in production.
- Logs must not become a shadow conversation store.
